### Tabby Architecture Overview

**1. General Structure & Paradigm**
Tabby (formerly Terminus) is a highly extensible, cross-platform terminal emulator. It is built fundamentally on two layers:
- **Frontend/Shell:** An Electron application featuring an Angular 15 frontend. The frontend is heavily modular and relies entirely on a plugin-based architecture.
- **Backend/Native Layer:** Historically relying on Node.js native modules (like `node-pty`, `serialport`, and `russh` via N-API), the project is currently in the process of porting these performance-critical, low-level system operations to a **Go backend**. 

**2. The Go Backend (`tabby-go`)**
The `tabby-go` subproject acts as a standalone binary spawned by the Electron main process. 
- **Communication:** It communicates with the frontend via **JSON-RPC 2.0** over standard input and standard output (`stdin`/`stdout`). This avoids IPC overhead native to Electron and guarantees cross-platform native execution.
- **Components:**
  - **SSH/SFTP (`pkg/ssh`, `pkg/sftp`):** Full SSH2 client connection manager, supporting port forwarding, agent forwarding, X11, interactive auth, and an SFTP file manager.
  - **PTY (`pkg/pty`):** Pseudo-terminal management using `creack/pty` on Unix-like systems. This replaces Node's `node-pty`. It manages the lifecycle, resizing, and output forwarding of local shell processes.
  - **Serial (`pkg/serial`):** Hardware serial port communication using `go.bug.st/serial`. Supports baud rate configurations, parities, and real-time streaming of serial data.
  - **Telnet (`pkg/telnet`):** Basic telnet connectivity and input/output routing.
  - **Native UI (`pkg/ui`):** Experimental bindings via CGo to `BTK` (a Qt-descended C++ UI framework), hinting at a potential future native, non-Electron GUI version.
- **Event Loop & Notifications:** The backend implements an asynchronous event notification loop. When data is received from PTY or Serial, it base64-encodes the bytes and emits a JSON-RPC notification (e.g., `"pty.data"` or `"serial.data"`) back to the Electron parent process.

**3. Frontend Plugin Architecture**
Everything in Tabby's UI is a plugin. Core functionalities are bundled as default plugins (e.g., `tabby-core`, `tabby-terminal`, `tabby-ssh`, `tabby-serial`, `tabby-settings`).
- **Angular Dependency Injection:** Plugins register themselves by providing classes to Angular DI tokens (Extension Points). For example, a new profile type is added by providing a `ProfileProvider`, and a new toolbar button is added via `ToolbarButtonProvider`.
- **xterm.js Integration:** The actual terminal emulation is handled by `xterm.js`, wrapped inside an Angular component in `tabby-terminal`.

**4. Design Decisions & Patterns**
- **Security & Vault:** Tabby features a built-in encrypted vault (`tabby-core/src/services/vault.ts`) for storing sensitive credentials like SSH passwords and keys, avoiding plain-text config storage.
- **Single Binary / Multi-role:** The Go backend serves as a versatile daemon handling multiple connection types asynchronously using Go's strong concurrency features (goroutines and channels).
- **Graceful Degradation:** The PTY and Serial packages are designed to fall back or return errors cleanly if the host OS does not support certain features (e.g., using `exec.Cmd` pipes if full PTY isn't available, though we just upgraded it to use `creack/pty`).

**5. Immediate Roadmap & Refactoring Strategy**
- The primary goal is to fully port all local PTY, Serial, and SSH session management from the Node/Electron native layer to the `tabby-go` JSON-RPC backend. 
- Ensure that the TypeScript frontend cleanly routes these connections to the Go backend instead of `node-pty` and `serialport`.
- Expand documentation (which I have started by creating/updating `ROADMAP.md`, `VISION.md`, `CHANGELOG.md`, `DEPLOY.md`, etc.) to maintain a clear path forward for future AI/human maintainers.

### Go Backend IPC Mechanism

- **Protocol:** `tabby-backend` runs a JSON-RPC 2.0 loop on standard input/output.
- **Logging:** It outputs logs (like "Starting Tabby Go backend") to **stderr**.
- **Data:** It expects line-delimited JSON-RPC objects on `stdin` and writes JSON-RPC objects on `stdout`.
- **Formatting:** A request looks like `{"jsonrpc": "2.0", "method": "ping", "id": 1}\n`. A response looks like `{"jsonrpc":"2.0","id":1,"result":{"status":"ok","version":"1.0.231-nightly.1"}}\n`.

### Electron Integration Plan

To integrate this in `tabby`, I will:
1. Create an `app/lib/goBackend.ts` file which:
   - Finds the `tabby-backend` binary based on platform/arch (in development, it's `build/tabby-backend`, in production it would be packaged).
   - Spawns the binary using `child_process.spawn`.
   - Listens to `stdout` and splits by newline to parse JSON.
   - Listens to `stderr` and maps it to `console.log`.
   - Maintains a Promise map for active requests (matching by `id`).
   - Maintains an EventEmitter for notifications (e.g. `pty.data`).
   - Exports a singleton instance `GoBackend` accessible from other main-process files.
2. Integrate `GoBackend` into `PTYManager` in `app/lib/pty.ts`.
3. Provide methods to support `PTYProxy` requests via IPC.

### Fixing Go Backend IPC Race Conditions

**Analysis of the Review:**
- The code reviewer correctly identified critical race conditions in my implementation of `PTY` and `SerialSession` wrappers.
- **Problem 1 (PTY Dropped Output):** Since `node-pty` was synchronous, the frontend immediately starts sending `resize` and `write` commands. Because `goBackend.request('pty.spawn')` is asynchronous, `goBackendId` is null when these arrive, and the commands are silently dropped.
- **Problem 2 (PTY ID Mapping):** If the Go backend sends `pty.data` immediately upon spawning, the frontend might receive the notification *before* the `pty.spawn` Promise resolves, meaning the `goIdToLocalId` mapping isn't set yet, dropping the initial terminal prompt.
- **Problem 3 (Serial Dropped Data):** In `SerialSession.start()`, `ipcRenderer.on('serial:data')` is attached *after* `await ipcRenderer.invoke('serial:open')`. Any data received between the port opening on the Go side and the IPC Promise resolving on the Node side is lost.

**Solution Strategy:**
1. **Invert ID Generation:** Instead of letting the Go backend generate the ID (`m.nextID`), I should pass the frontend-generated UUID (`id`) down to the Go backend as part of the `pty.spawn` and `serial.open` payload. This eliminates the need for a reverse mapping (`goIdToLocalId`) entirely! The Go backend will just use the provided ID.
2. **Buffer Pre-Ready Commands:** If the frontend calls `resize` or `write` before the Go backend acknowledges the spawn, I should buffer those commands in arrays and replay them once the `spawn` Promise resolves.
3. **Attach Listeners First:** For `tabby-serial`, I must attach the `ipcRenderer.on` listeners *before* calling `invoke('serial:open')`.

### Project Context: Tabby Go Port

**1. Ultimate Vision & Architecture**
- **Tabby** (formerly Terminus) is a highly extensible, cross-platform terminal emulator designed to unify remote and local computing tasks.
- **Frontend Paradigm:** It uses an Electron app shell with an Angular 15 frontend. Every UI element and core feature is bundled as an isolated Angular plugin (e.g., `tabby-core`, `tabby-terminal`, `tabby-ssh`, `tabby-local`, `tabby-serial`). Extensions interact with the core via Angular Dependency Injection (e.g., `ToolbarButtonProvider`, `ProfileProvider`).
- **Backend Paradigm:** The project is migrating away from Node.js native bindings (`node-pty`, `@serialport/bindings-cpp`, `russh`) towards a unified, standalone **Go backend (`tabby-go`)**. This transition is critical to improve performance, maintainability, and decouple the application from the V8 engine, setting the stage for future native (non-Electron) GUI toolkits (like BTK) and mobile apps.

**2. Go Backend Integration Mechanics**
- **The IPC Bridge:** The Electron main process launches the Go binary (`tabby-backend`) as a long-running daemon on application startup (`GoBackendService` in `app/lib/goBackend.ts`).
- **Protocol:** Communication happens exclusively via **JSON-RPC 2.0 over standard input and output streams** (`stdin` / `stdout`). The Node process uses `split2` to parse the line-delimited stream.
- **Asynchrony vs. Synchrony:** Many of Tabby's native Electron plugins expect synchronous initialization (e.g., returning a UUID immediately upon requesting `pty:spawn`). The IPC Bridge respects this by generating local UUIDs on the frontend, passing them into the JSON-RPC payload, and storing a mapping to correctly route asynchronous backend stream events (`pty.data`, `serial.data`) back to the specific Angular components via `app.broadcast` and `ipcRenderer`.
- **Packaging:** The `tabby-backend` binary must be explicitly included in `electron-builder.yml` (`extraResources: build/tabby-backend*`) to ensure the production app does not crash. Path resolution between development (where `appPath` is `app/lib`) and production (where `appPath` is `app/dist` or inside an `app.asar` archive) is handled conditionally inside `GoBackendService`.

**3. State of the Port**
- **`tabby-local` (PTY):** Fully ported. Replaced `node-pty` with the Go package `github.com/creack/pty`. `PTYManager` now sends `pty.spawn`, `pty.resize`, `pty.write`, and `pty.kill` requests down the IPC bridge. Backpressure control (`pty.pause`/`resume`) is stubbed via JSON-RPC.
- **`tabby-serial` (Serial):** Fully ported for Desktop via Go's `go.bug.st/serial`. `SerialSession` and `SerialService` were stripped of `@serialport` imports. **Crucial Pattern:** Because Tabby runs in browsers as a Web App, direct `import { ipcRenderer } from 'electron'` crashes the Webpack build. Instead, we use `window.require('electron')` for desktop, and preserve `WSABinding` (the Web Serial API) as a fallback for `Platform.Web`.
- **`tabby-ssh` and `tabby-sftp`:** Integration is PENDING. These plugins utilize extremely complex state machines spanning thousands of lines wrapped around the `russh` Node module. Attempting to port them line-by-line is error-prone. The required architectural shift (replacing synchronous stateful clients with async JSON-RPC callbacks) is documented as the highest priority task in `TODO.md` and `ROADMAP.md` for the next development phase.

**4. Documentation Standards**
- Documentation is a first-class citizen. `ROADMAP.md`, `TODO.md`, `VISION.md`, `CHANGELOG.md`, and `MEMORY.md` serve as the source of truth for the overarching architecture, current sprint status, and handover instructions.

**Overview of `SSHSession` Analysis**
To wire up `tabby-ssh/src/session/ssh.ts` to the Go backend (`tabby-go/pkg/ssh` via JSON-RPC), we must completely overhaul the `SSHSession` class. It currently leverages the Node.js native `russh` module extensively.

The `SSHSession` class extends `BaseSession` and handles:

2. **Host Key Verification:** Handled via an asynchronous callback passed directly into `russh.SSHClient.connect()`.

6. **I/O (`write()`, `resize()`, `kill()`):** Interacts with the `russh.Channel`.
7. **Port/X11 Forwarding:** Uses `channel.requestX11()` and `ssh.forwardLocalPort()`.

**The New Go IPC Paradigm**
The Go backend simplifies this entire state machine. 
- Calling `goBackend.request('ssh.connect', params)` takes a complex configuration object (`host`, `port`, `user`, `auth`, `jumpHost`, `algorithms`, etc.) and handles the transport and authentication internally. It returns a generic string `connectionId`.

The frontend must listen for these, show the UI modals, and reply with `ssh.verifyHostKey` or `ssh.keyboardInteractiveResp`.
- **Shell Creation:** Calling `goBackend.request('ssh.startShell', { connectionId })` opens the PTY and returns a `sessionId`.
- **I/O:** `goBackend.request('ssh.write', { connectionId, sessionId, data })`.

Because `russh` types are scattered everywhere (method arguments, return types, properties), I must replace the entire file content rather than attempting to patch it. # Tabby Terminal - Project Architecture & Migration Memory

## 1. Project Overview & Architecture
Tabby is a highly extensible, cross-platform terminal emulator. 
*   **Frontend**: Built with Angular (currently ~v15) and heavily utilizes RxJS for event streams (Observables/Subjects). UI styling uses Bootstrap and `ng-bootstrap` for modals.
*   **Desktop Shell**: Electron, using a multi-process architecture where the Angular app runs in the Renderer process, and OS-level interactions (file system, window management) are handled in the Main process.
*   **Plugin System**: The application is divided into core modules (`tabby-core`, `tabby-terminal`) and specialized feature plugins (`tabby-ssh`, `tabby-local`, `tabby-serial`, `tabby-sftp`, `tabby-telnet`). Plugins are dynamically loaded and rely heavily on Angular's Dependency Injection (`Injector`).

## 2. The Go Backend Migration Strategy (Current Initiative)
The core goal of our current development phase is to eliminate brittle, hard-to-compile Node.js native dependencies (`node-pty`, `serialport`, and the pure-JS but complex `russh` library) by porting the backend heavy-lifting to a unified Go daemon (`tabby-go`).

*   **Communication Bridge**: 
    *   The Electron Main process spawns the compiled `tabby-go` binary as a child process.
    *   Communication happens over `stdin`/`stdout` using **JSON-RPC 2.0**.
    *   The Electron Main process acts as a router (`app/lib/goBackend.ts`), exposing `ipcMain.handle` endpoints that the Angular renderer calls via `ipcRenderer.invoke`.
*   **Why Go?** Go provides robust, statically compiled, cross-platform concurrency for PTY management (`creack/pty`), Hardware Serial (`go.bug.st/serial`), and SSH/SFTP (`golang.org/x/crypto/ssh`). This removes the need for `node-gyp` native recompilations during Electron upgrades.

## 3. SSH & SFTP Subsystem Refactoring (In Progress)
The `tabby-ssh` plugin historically coupled the UI directly to the `russh` library inside the renderer process.
*   **Previous Pattern**: `SSHSession` instantiated `russh.SSHClient`, handled encryption, multiplexing, and direct socket management in the UI thread.
*   **New Pattern (Facade)**: `SSHSession` is being rewritten as a frontend proxy. It communicates connection parameters, keyboard-interactive authentication prompts, and window resize events via IPC to the Go backend.
*   **Mock Interfaces**: Because the rest of the app (`SSHShellSession`, `SFTPSession`) expects `russh`-like Channel objects, we created `MockChannel`. This class mimics the data streams (`data$`, `eof$`, `write()`, `resizePTY()`) but pipes everything through the IPC bridge to the Go daemon.

## 4. Key Design Patterns & Technologies
*   **RxJS Event Streams**: Everything from terminal keystrokes to lifecycle hooks (`willDestroy$`, `destroyed$`) to SSH auth prompts uses RxJS `Subject`s. Memory leaks are avoided by meticulously completing these subjects and unregistering IPC listeners on teardown.
*   **Angular Dependency Injection**: Services (`LogService`, `PasswordStorageService`, `SSHKnownHostsService`) are injected everywhere. When creating non-Angular classes (like `SSHSession`), we pass the `Injector` manually to preserve access to the DI container.
*   **Webpack & Strict TypeScript**: The build system uses Lerna/Yarn workspaces with Webpack. The TypeScript compiler runs in a strict mode that aggressively fails the build on unused imports, type mismatches (e.g., removing `russh` caused cascading type failures), and unhandled promises.

## 5. Known Hurdles & Workarounds
*   **TypeScript Strictness during Refactoring**: Ripping out a core dependency like `russh` causes massive type breakages. Our strategy is iterative patching: replacing concrete `russh` types with `any` or facade classes (`MockChannel`), stripping unused imports, and mocking synchronous getters (`get open()`, `get fullyAuthenticated()`) to satisfy Angular component templates.
*   **Asynchronous IPC vs Synchronous State**: The old `russh` implementation allowed synchronous access to channel state. Moving to Go requires asynchronous IPC (`ipcRenderer.invoke`). We work around this by maintaining local cached state in the proxy classes.
*   **Platform-specific implementations**: E.g., OpenSSH agent forwarding requires handling Named Pipes on Windows (`\\.\pipe\openssh-ssh-agent`) vs Unix sockets (`SSH_AUTH_SOCK`) on macOS/Linux.

## 6. Current Status & Next Steps
*   **Completed**: PTY and Serial port Go backend integrations. Go JSON-RPC test suite. Version mismatch fixes.
*   **In Progress**: Fixing the final TypeScript compilation errors in `tabby-ssh` after removing `russh`. Specifically, ensuring `MockChannel` has all the dummy methods (`take`, `requestPty`, `requestShell`) needed by `tabby-ssh/src/session/shell.ts`.
*   **Next Up**: Once the `tabby-ssh` Webpack build passes, we will perform end-to-end integration testing of the SSH terminal and SFTP panel against the Go backend daemon.
